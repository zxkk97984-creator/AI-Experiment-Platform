# 人工智能基础实验平台架构设计总览

> 文档状态：当前实现说明（2026-10-09）。本文以代码、配置、迁移和 CI 为事实来源。

## 1. 系统定位

人工智能基础实验平台面向人工智能、机器学习和深度学习课程，提供从课程学习、在线实验、作业/考试提交到自动判题、AI 辅助评分和教师复核的完整教学闭环。

当前正式产品路径是 `frontend/` + `backend/`。仓库不再包含独立的静态设计稿前端；设计规范以 [`dai-design-system-v2.md`](dai-design-system-v2.md) 和真实 Vue 组件为准。

## 2. 总体拓扑

### 2.1 本地开发

```text
浏览器 :5173
    │ Vite /api 代理
    ▼
FastAPI :8000（宿主机）
    ├── MySQL 8.4 :3306（Docker，127.0.0.1）
    ├── Redis 7.4 :6379（Docker，127.0.0.1）
    ├── Judge Worker（宿主机）
    │      └── Docker Socket → 判题容器
    ├── Account Worker → 名单导入 / 批量账号任务
    ├── Lab Worker → 训练、推理、评分、租约恢复
    └── Environment Builder Worker（宿主机）
           └── Docker Socket → 环境镜像构建 / Registry
```

`scripts/dev-up.sh` 负责启动数据库、迁移、判题镜像、API、Judge / Environment Builder / Account Worker、按配置启用的 Lab Worker 和 Vite；API 与 Worker 使用 `backend/.env`，Vite 使用 `VITE_API_PROXY_TARGET` 指向 API。

### 2.2 生产部署

```text
浏览器
    │
    ▼
frontend 容器（Nginx :80，宿主机默认 :8080）
    │ /api 反向代理
    ▼
api 容器（FastAPI :8000）
    ├── mysql 容器（内部网络 :3306）
    ├── redis 容器（内部网络 :6379）
    ├── Docker Socket → 判题 / Notebook Kernel 容器
    └── 外部 AI 服务（仅显式启用并通过数据治理审批时）

worker 容器 ───────────────┘
environment-builder 容器 ── Docker Socket → 环境镜像 / Registry
account-worker 容器 ─────── 数据库账号后台任务
lab-worker 容器 ─────────── Docker 实验执行、持久队列与恢复

migrate 容器：一次性执行统一 bootstrap，成功后 api / worker / environment-builder / account-worker / lab-worker 才启动；ai-worker 仅在 `ai` profile 显式启用
```

生产编排由 `docker-compose.prod.yml` 定义，服务为 `mysql`、`redis`、`migrate`、`api`、`worker`、可选 `ai-worker`、`environment-builder`、`account-worker`、`lab-worker` 和 `frontend`。MySQL、Redis 不发布宿主机端口，只加入 `internal` 网络；需要执行 Docker 的服务显式或通过 Compose extends 挂载 `/var/run/docker.sock`。AI worker 默认不启动。

## 3. 运行模式与入口

| 模式 | 配置 | 入口 | 说明 |
| --- | --- | --- | --- |
| 本地开发 | `docker-compose.yml` | `./scripts/dev-up.sh` | MySQL/Redis 在 Docker；API、Worker、Vite 在宿主机 |
| 本地手动 | 同上 | `uvicorn app.main:app` | 适合只调试 API 或单独 Worker |
| 生产 | `docker-compose.prod.yml` | `docker compose ... up` | 迁移、API、Worker、环境构建和 Nginx 全部容器化 |
| E2E 本地覆盖 | `docker-compose.prod.yml` + `docker-compose.e2e-local.yml` | Compose 多文件命令 | 将 MySQL/Redis 映射到宿主机 `3309/6380` |
| Legacy Jupyter | `docker-compose.yml` profile `legacy-jupyter` | `docker compose --profile legacy-jupyter up -d jupyter` | 兼容路径，默认不启动；新流程使用内置 Notebook Player |

本地 API 的 ASGI 对象是 `app.main:app`；生产镜像使用 `app.main:create_app --factory`。数据库迁移不会由 API 启动自动执行，必须显式运行 Alembic 或使用生产 `migrate` 服务。

### 4.2 服务层与 Worker

`backend/app/services/` 负责认证、课程访问、作业/考试判题、实验和 Studio、AI、环境构建、存储对象、通知、搜索、统计与运维指标等业务逻辑。`backend/app/worker/` 当前有四个进程入口（Judge 入口按角色启动独立进程）：

- `python -m app.worker.judge_worker`：默认只消费作业/考试队列，执行 Docker 沙箱/Kernel 任务并负责唯一 stale recovery；`DAI_WORKER_ROLE=ai` 时仅消费 AI 队列，且需显式启用 AI；
- `python -m app.worker.environment_builder_worker`：消费环境构建任务，对账数据库任务状态，执行环境镜像构建并在 V2 模式下校验 Registry digest。

- `python -m app.worker.account_worker`：独立处理名单导入、批量账号等任务。
- `python -m app.worker.lab_worker`：仅在实验功能启用时处理数据库 Lab 队列、租约恢复和批量重评；使用 `(created_at, id)` 游标每批最多扫描 100 个候选，每趟固定上界，避免队首不可运行任务阻塞后续任务。

Judge 在每轮消费前检查恢复期限，即使队列持续繁忙也会恢复；Redis 网络超时与失败退避有界。消息 `RPUSH` 入队、`BLPOP` 出队，取到消息后将该队列移至候选末尾。AI 角色仍只消费 AI 队列。升级必须协调重启所有消费者，不能与旧 `BRPOP` 消费者混跑，也不应删除现存消息。

API lifespan 只运行过期考试扫描和空闲 Kernel 清理；判题恢复由 Judge Worker 负责，避免多个 API 实例重复恢复。

## 6. 数据与持久化

### 6.1 MySQL 与 Alembic

SQLAlchemy 模型集中在 `backend/app/models/__init__.py`，迁移位于 `backend/alembic/versions/`。主要领域包括：

- 用户、学期、教学班、课程、章节、课时、选课和学习进度；
- 作业、判题题目、提交、考试、题目、答案和成绩；
- Notebook 模板/版本、实验模块/记录/提交、Studio 资源清单；
- Rubric、CodeGrade、教师改分、公告、通知和用户偏好；
- StorageObject/StorageQuarantine，以及环境档位、版本、草稿、发布和构建任务。

MySQL 是业务记录、提交状态、考试状态、环境构建任务和发布关系的主要事实源。Redis 队列丢失时，Worker 依据 MySQL 中的 queued/pending/running 状态执行恢复和重新唤醒。

### 6.2 Redis

Redis 用于：

- Refresh Token 消费状态与 Access Token 黑名单；
- 判题、考试、AI 评分和环境构建队列的唤醒消息；
- 登录限流、短期租约、环境构建 heartbeat 和运维指标。

Redis 不是提交、考试答案或环境构建任务的唯一事实源。生产 Compose 开启 AOF `everysec`，本地 Compose 仅使用开发数据卷。

**客户端契约**（`app/redis_client.py`）：API 侧统一使用连接/读取各 0.5 秒、零自动重试、连接池上限 32 的有界客户端（lifespan、依赖惰性初始化、ready fallback 共用同一工厂）；指标使用独立客户端（各 0.1 秒）。认证关键操作（黑名单 EXISTS、登录限流、刷新 GETDEL/SETEX、退出写黑名单）在 Redis 故障时统一返回 `503 SERVICE_UNAVAILABLE`，绝不当成"令牌不存在"或放行；GETDEL 结果未知时不重放，提示重新登录。阻塞队列 Worker 保留各自的独立策略。

**HTTP 指标**：每进程一个固定大小聚合器（键空间 = 白名单指标 × 白名单标签），请求路径只更新内存计数、无 I/O；单个后台任务每秒 flush 一次（最多一个在途）。flush 失败丢弃该批并计数（日志限频），关闭时最多 1 秒 best-effort flush，不落盘、不重放、不新增队列。

### 6.3 文件与对象存储

业务文件通过 `backend/app/storage/` 的统一 Storage contract 访问：

- 开发默认 `local`，目录为 `backend/storage/`；
- 生产可切换到 provider-neutral 的 `s3`，使用 S3-compatible endpoint、bucket、region 和凭据；
- 课程封面、课时视频、Studio 资源和 Notebook 运行文件由各自服务管理；
- 数据库保存逻辑 object key 和对象元数据，`storage_objects` / `storage_quarantines` 负责生命周期与对账。

生产 local fallback 使用 `studio_data`、`lab_data`、`video_data`、`cover_data`、`material_data` named volume；生产必须将卷和对象存储纳入备份与恢复演练。

## 7. 关键数据流

### 7.1 认证

```text
POST /api/v1/auth/login
    → 校验 MySQL 用户和密码 / Redis 限流
    → JSON 返回 access_token、expires_in、user
    → refresh token 写入 HttpOnly dai_refresh_token Cookie
```

Access Token 默认 30 分钟，Refresh Token 默认 7 天。刷新优先消费 Cookie 中的 Refresh Token，旧令牌通过 Redis GETDEL 失效；登出撤销 Refresh Token 并加入 Access Token 黑名单。生产环境 Cookie 使用 `Secure`。

### 7.2 作业判题

```text
学生提交（可带 client_request_id）
    → API 校验输入、权限；先查幂等键（同键同正文返回原提交，同键不同正文 409 IDEMPOTENCY_KEY_REUSED）
      —— 幂等查询先于次数与截止限制；省略键的旧客户端保持原行为
    → MySQL 写入 Submission / CodeGrade
    → Redis 只负责唤醒 judge_worker
    → Worker 条件抢占 queued → running（同时铸造本次认领代次 claim_token）
    → Docker 判题容器运行 pytest
    → MySQL 在"仍持有本次认领"的条件 UPDATE 内写回状态、计数、分数和结果
    → 前端轮询结果
```

**结果修订号（result_revision）**：`submissions` / `exam_answers` / `code_grades` 各有一个
只增不减的整数修订号，由任何产生或改变结果的写入（判题终态、AI 终态、人工改分、受控重评）
在**同一事务**内原子 +1。人工评分与旧客户端携带 `expected_result_revision` 即可拒绝过时写入，
无需内容比对或时间戳。退回 `pending` 的可重试失败不是结果，不推进修订号。

**主结果与后续评分记录同事务**：作业/考试的判题收尾把「受认领保护的终态 UPDATE」与
`CodeGrade` 创建（含来源证据：判题认领标识、结果修订号、评分版本）放进同一个事务；
失去代次立即回滚并停止——不创建评分记录、不推送 AI、不推进考试汇总。关联写入失败
（唯一约束冲突等）同样回滚主结果，绝不允许出现"有正式分、没有评分记录"的分裂状态。

**恢复扫描复核"实际仍然过期"**：`requeue_stale_jobs` / `recover_stale_ai_grades` 的条件
UPDATE 除认领代次外还必须带实时过期谓词（判题按 `coalesce(heartbeat_at, started_at)`，
AI 按 `started_at`）。SELECT 与 UPDATE 之间续过心跳的活任务因此不会被旧扫描结果重置。

**认领代次（claim_token）与结果栅栏**：判题任务的状态机在 `submissions` / `exam_answers` /
`code_grades` 上各有一个 `claim_token`，由 `claim_job` / `claim_ai_grade` 在 `queued → running`
的条件 UPDATE 中现生成。**所有结果、状态、分数与派生记录（含 active 模式写入的正式分）
必须在同一条带 `claim_token`（与 `grading_status='running'`）条件的 UPDATE 内提交**，
一次事务完成"确认写入资格 + 写结果 + 置终态"。失去认领（恢复机制已重新排队并由别的 Worker
接管）的旧 Worker 因此无法覆盖新结果：CAS 未命中即记 WARNING 并**丢弃**该结果，由恢复机制
兜底重排，不重试、不回写。

代次**不能复用 `attempt_count`**：后者是重试预算，会被教师/管理员重试路径重置为 0，
重置后重新入队会让旧代次重新命中，等于把本缺陷重新引入。这也是本仓库既有的做法
（`LabRun.lease_token`、`EnvironmentBuildJob.lease_token`）。

**存活判定与恢复阈值**：`running` 的存活信号是 `heartbeat_at`（认领时写入，判题在**测试组之间**
续期；AI 支路在每次客户端重试前续期），未续期则回退 `started_at`。超过
`DAI_JUDGE_STALE_RUNNING_SECONDS`（默认 1800 秒；须覆盖"组数 × 每组超时 + 容器启动 + 镜像拉取"
的最坏墙钟）才判定为失联。恢复扫描的 running 重置也用 `claim_token` 作栅栏（NULL 安全比较），
不再用会被 MySQL `DATETIME(0)` 截断的 `started_at`。AI 队列的 `STALE_RUNNING_SECONDS` 同为 1800
（AI 客户端最多重试 3 次 × 60–180 秒，600 秒会把合法运行判为失联并白跑一遍）。

**滚动升级顺序（重要）**：先执行迁移 → 协调重启全部消费者 → 再上新代码。旧 Worker 认领的行
`claim_token` 为 NULL，会被要求 token 相等的新代码拒绝，由恢复扫描重置后重新铸造代次。

正式判题容器使用无网络、非特权、只读根文件系统、资源限制和非 root 用户等隔离参数；实际参数以 `backend/app/worker/judge_worker.py` 为准。

判题结果必须**可验证**才允许自动计分：测试组结果行必须恰好一条、计数为有界非负整数、与进程退出码一致，且退出码 0 必须伴随 pytest 汇总行（缺少汇总行说明 pytest 未汇报就退出，如 `os._exit(0)`）。任一不满足即视为不可验证，走 `system_error`（`score=None`、可重试、不扣分），**不按 0 分计入**；平台自身故障也不消耗学生的 `max_attempts` 名额。这一层是**立即减损**，不是完整安全修复——学生代码与 pytest 插件同解释器的问题由数据型用例 + 可信侧判定解决（见下文 AI/判题信任边界与 `judge_trusted_runner` 开关）。

### 7.3 实验与 Notebook

实验记录和单元内容由 `/api/v1/experiments` 管理，内置 Notebook Player 使用 `ExperimentRecord`、Kernel Manager 和绑定的环境版本执行单元。Studio 负责模板草稿、不可变版本、导入导出、资源清单和预览。

旧 `/api/v1/notebooks` 已停止进程内转发，所有旧路径返回 `410 DEPRECATED` 并带迁移提示。新客户端不得新增对该路径的依赖。

### 7.4 AI 评分

代码题支持 `legacy`、`shadow` 和 `active` 评分模式。AI 服务通过配置的兼容 API 调用；输出先经过 schema、分数范围、维度权重和重复扣分校验，再由 `finish_ai_grade` 在**一次受认领保护的事务**内写入终态：合法结果 = `completed`，需要人工复核 = `review_required`。评分字段、完成时间、认领释放与 active 模式的正式分同生共死；Worker 不再有第二次完成操作。失去认领抛 `LostClaimError` 并直接停止（不写失败态，交给恢复机制），其他异常仍走有界错误处理。

必需静态分析器（Ruff / Radon，均为运行依赖）故障时**不调用外部 AI、不生成自动正式总分**，经同一认领栅栏转 `review_required` 人工复核；`analyze_python` 返回逐工具的 `tool_status`（ok/unavailable/timeout/invalid_result/error/not_run）与总体 `status`，语法错误与平台工具故障分开报告。教师可复核和覆盖。

生产 AI 开关默认关闭，启用前必须完成 [`ai-data-governance.md`](ai-data-governance.md) 的审批门；关闭时不外呼，人工评分路径仍可用。

### 7.5 环境档位

环境编辑器 V2 以数据库 draft 为事实源：

```text
管理员编辑草稿
    → Python / pip / apt 包规范化与候选校验
    → Redis 唤醒 environment-builder
    → Docker 构建、smoke、推送和按 digest 回拉
    → 版本 available
    → 管理员发布不可变版本
    → 教师选择当前可用版本；已绑定记录继续使用原版本
```

生产环境基础镜像必须使用 digest。V2 的迁移顺序、Registry Secret 和回滚规则见 [`environment-profiles.md`](environment-profiles.md)。

### 7.6 教学只读与成绩簿

学期关闭、班级归档和实例停用在策略锁保护的同一事务内检查 `started` 考试；不按当前受众过滤，也不因超过结束时间而忽略。存在记录时返回 `409 EXAMS_IN_PROGRESS`，需要先收卷。学生写请求在写入事务中重查当前授权；考试批量保存逐题重新检查。历史 GET 保持只读，系统收卷及已受理评分继续完成。

成绩簿按授课实例批量加载本班学生的题目、提交和评分，保留 Decimal 计算、缺交/待评阻断、来源证据、预览摘要、发布锁及历史快照。读取按主键顺序锁定，不跨请求缓存。前端班级、历史版本和导出请求共享上下文失效规则，迟到响应不能覆盖新选择。

## 8. 接口与配置契约

- 作业进度：`GET /api/v1/assignments/{assignment_id}/my-progress`，仅当前学生且通过受众校验。返回 `{items: [{question_id, latest_submission_id, status, completed}]}`；最新按最大提交 ID，`completed` 为历史存在 `accepted` / `graded`，无提交的 ID 和状态为 `null`。代码通过原结果接口按需读取。
- 作业页面按题目保留内存草稿，并使切题/卸载前的历史、自测和提交响应失效。结果详情采用串行轮询、隐藏暂停、可重试错误态；403/404 停止，连续五次临时失败后停止自动请求。
- 所有业务 API 前缀为 `/api/v1`；运行时 OpenAPI 为 `/docs`，JSON schema 为 `/openapi.json`。
- 存活检查：`GET /api/v1/health/live`；就绪检查：`GET /api/v1/health/ready`，同时检查 MySQL 和 Redis。
- 错误响应统一为 `detail.code`、`detail.message`、`detail.fields`，环境编辑器校验还会返回 `field_errors`。
- 开发配置从 `backend/.env` 加载；生产 Compose 从根目录 `.env` 和 Docker Secret 加载。
- 环境变量示例分别为根目录 `.env.example`（生产）和 `backend/.env.example`（开发）；不要提交实际 `.env` 或 Registry 凭据。

## 9. 验证与维护边界

后端测试分三组：`tests/automated`（默认收集，隔离 SQLite + fakeredis）、
`tests/native_http`（**独立目录**，真实 Uvicorn 子进程 + 独立数据库/Redis，覆盖生命周期、
到期扫描、慢 Redis、关闭时限；`pytest.ini` 的 `testpaths` 不含它，必须显式运行，CI 有独立 job）、
以及可选的真实 Docker/MySQL/Nginx 组。原生组显式使用
`trust_env=False` 的本机 HTTP 客户端，避免宿主代理环境影响结果。

CI 当前包含：

- Python 3.12 的 SQLite 和 MySQL 双库 pytest；
- Ruff 高信号规则、pip-audit 接受记录、Alembic drift check；
- Node.js 20 的 ESLint、Vitest、生产构建和生产依赖审计；
- 需要 Docker 的 Playwright E2E 和生产 Compose smoke；
- 独立 `lab-runtime` CPU 实测门禁，实际执行 Judge / Lab 容器测试，JUnit 出现失败、错误、跳过或没有测试均阻断。PyTorch、GPU 另行验收。

常用本地命令和部署顺序见根目录 [`README.md`](../README.md)。各领域实现和运行说明见 README 的当前文档地图。
