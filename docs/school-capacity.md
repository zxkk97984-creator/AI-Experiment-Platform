# 教学平台容量验证

目标是在**计划部署的服务器**上，用 200 个独立测试学生持续 30 分钟发送混合请求。目标服务器尚未部署，因此本仓库提供验证工具和可重复执行步骤；本地单元测试、浏览器流程和 Docker 实验通过不能代替该容量证据。

## 准备专用测试班

由管理员建立专用测试学期、教学班、授课实例和 200 个测试学生，完成首次改密，并为每人准备独立实验记录。实验应使用实际生产镜像、队列、资源限额和评分模板，包含一个可以运行、已经配置 Cell 检查的代码单元格。实验的正式提交次数、截止时间及评测版本应足以完成预定负载。测试成绩只留在这些测试班中。

脚本不会创建、改密或转移任何账号，不会发布成绩，也不会修改班级配置。它只使用清单中的账号和记录；登录后的预检重新核验学生身份、记录所有者、课程和授课实例，任何人不符则整体终止。清单必须显式列出允许的测试授课实例，学号作为字符串保留前导零。不要填写真实教学班或真实学生凭据。

凭据清单放入已被 Git 忽略的 `.runtime/school-verification/`，文件权限设为 `0600`。示例仅展示结构，需要填写学校测试数据并扩展到 200 个不同账号和记录：

```json
{
  "base_url": "https://teaching-staging.school.example",
  "allowed_offering_ids": [101],
  "students": [
    {
      "username": "00000001",
      "password": "测试学生已经修改的密码",
      "course_id": 11,
      "offering_id": 101,
      "record_id": 1001,
      "cell_id": "first-code-cell"
    }
  ]
}
```

`base_url` 是站点来源，不能含路径、查询参数或账号信息。远程地址要求 HTTPS；本机允许 `http://127.0.0.1:端口`。脚本验证证书，不提供跳过 TLS 校验的开关。每个学生有独立 HTTPX 客户端、Cookie 和访问令牌；访问令牌到期前刷新自己的会话，不把一个账号复制成 200 个并发用户。

## 执行

使用仓库后端虚拟环境，其中 HTTPX 版本与后端依赖一致。先仅验证清单，不发 HTTP 请求：

```bash
chmod 600 .runtime/school-verification/manifest.json
backend/.venv/bin/python scripts/verify_school_capacity.py \
  --manifest .runtime/school-verification/manifest.json --validate-only
```

默认是 200 人、预检登录分散在 60 秒内、全部预检成功后持续测量 1800 秒，每人平均约 2 秒发送一次操作，读取与运行权重为 80:20。正式提交默认禁用。读取包含清单课程详情、课程资料、授课实例详情、本人实验记录。运行先执行该学生记录中指定代码单元格的现有源码，再排入后台 Cell 检查；已有检查未结束时延后下一次运行。脚本不替换源码。

完整混合负载需**显式启用正式提交**。默认每人最多发起一次正式提交，重复操作仍计入尝试上限；每次请求使用新的幂等 UUID。按实际实验上限规划 `--max-submissions-per-user`，避免重复提交的相同成果消耗请求却不能形成新的有效评测。

```bash
backend/.venv/bin/python scripts/verify_school_capacity.py \
  --manifest .runtime/school-verification/manifest.json \
  --users 200 --duration 1800 --ramp-seconds 60 --interval 2 \
  --read-weight 80 --run-weight 15 --submit-weight 5 \
  --allow-formal-submit --max-submissions-per-user 1 \
  --report .runtime/school-verification/target-200-users/report.json
```

只读冒烟可以设置 `--run-weight 0 --submit-weight 0`，并缩短时长、减少人数。这类报告会明确标记混合证据不足，不能作为完整混合负载验收。脚本不会根据命令参数降低服务端登录限流或运行资源准入限制。需分散登录或配置测试环境的合法负载来源；发生 429 应记录和诊断。

## 读取结果和停止

`report.json` 保存最终结果；同目录 `progress.json` 每 15 秒原子更新一次，用于观察长测试和定位异常中止。输出只保存聚合计数和延迟，不保存站点地址、学号、密码、令牌、Cookie、记录 ID 或响应正文。延迟采用有界直方图，p95 是桶上界：2 秒内精度为 1 毫秒、2–10 秒为 10 毫秒、10–120 秒为 100 毫秒；更长的排队等待使用指数桶，不会把长队列截断成 120 秒。长时间运行不会不断积累样本。

- 普通读取单独计算 p95，目标不超过 1000 毫秒；读取错误不能作为成功读取计算通过。
- 已接受的正式提交确认单独计算 p95，目标不超过 2000 毫秒；后台排队和评分完成时间另外统计。
- 运行、排队状态转换、恢复状态、终态失败、HTTP 准入失败、提交限额和队列等待时间单列。未知错误只记录 HTTP 状态或固定类别，不保存服务端错误正文。
- `evidence_complete.200_students_30_minutes` 要求 200 人都成功预检且完整测量 1800 秒；`read_run_formal_submit_observed` 要求三类请求都确实发生。
- `runtime_recovery_and_disk_limits` 始终为 `false`。仅看到 HTTP 的 `recovering` 状态不足以证明容器残留已清理、租约恢复正确和磁盘超限已被隔离。

`Ctrl+C` 或 `SIGTERM` 停止新请求，取消当前客户端等待，写出中断报告。请求设有整体超时；报告记录停止时结果未知的请求及未完成任务。脚本不自动重试结果未知的提交，不自动取消或删除已接受的后台任务；结束后应由管理员核对测试班队列、容器和成绩。`SIGKILL` 无法完成收尾，最后一份 `progress.json` 仍只是运行中快照。

退出码：`2` 表示清单或参数不正确；`1` 表示没有达到完整混合 HTTP 门槛（包括有意执行的短测试、只读测试、中断或错误）；`0` 表示 200 人 / 30 分钟、读取 / 运行 / 正式提交、延迟及错误门槛均通过。**退出码 0 仍不能独自批准上线。**

## 配套运行证据

在同一目标服务器另行保存 CPU、内存、磁盘空间、MySQL 连接池、Redis 队列和 Worker 日志的时序证据，记录服务器规格、镜像 digest、版本、运行并发、资源预算和测试时间。用独立测试实验核验满容量准入、排队释放、Worker 中断后的恢复、超时 / 内存 / 磁盘限额和残留容器清理。使用真实 Docker 环境，分别确认恢复后的任务不会覆盖教师调分或重复计入正式提交次数。

TLS、不可变镜像、真实备份恢复、容量和上述运行隔离证据齐备后，才能按仓库生产验收要求安排试点班。清单含秘密，应由管理员按学校测试数据保留期限安全删除；聚合报告可以保留为无账号的容量证据。
